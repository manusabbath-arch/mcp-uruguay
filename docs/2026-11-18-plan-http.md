# Plan de arquitectura: transporte HTTP remoto (M8)

Guardado el 2026-11-18. Responde a M8 de `docs/2026-11-15-plan-fable5.md`, que exige diseñar esto
antes de implementarlo: "diseñar tres cosas: caché compartida entre usuarios, límite de pedidos
para no cargar a las fuentes, y qué hacer con `diagnostico`, que devuelve una ruta del disco."

El SDK ya pineado (`mcp==2.3.0`) soporta el transporte `streamable-http` de fábrica
(`MCPServer.run_streamable_http_async`, que expone `streamable_http_app()` como app de Starlette).
No hay que construir un transporte: hay que decidir qué ponerle alrededor antes de exponerlo.

## 1. Caché compartida entre usuarios

**Decisión: no hace falta ningún mecanismo nuevo.** Las 29 herramientas son de solo lectura y
devuelven exactamente el mismo dato para los mismos parámetros, sin personalización por usuario
(no hay cuentas, no hay auth). En modo remoto, un solo proceso sirve a N clientes concurrentes y ya
comparten el mismo directorio de caché (`cache.directorio()`), que es justamente lo que se quiere:
el segundo cliente que pide el mismo dato lo recibe de la copia que bajó el primero, sin volver a
pegarle a la fuente.

Lo que sí hace falta — y ya está resuelto por M2 — es que dos requests concurrentes que refrescan el
mismo archivo vencido no se corrompan entre sí (patrón `.nuevo` + reemplazo atómico, con sufijo único
por proceso). Antes de desplegar remoto, correr `pytest -k concurrente` o similar para confirmar que
ese patrón cubre **todos** los caminos de escritura de caché, no solo `bcu_serie` (que fue el caso
que motivó M2). Si algún lector todavía hace `unlink()` antes de descargar, hay que llevarlo al mismo
patrón antes de exponer el servidor a tráfico concurrente real.

**Cómo falla si esto está mal:** dos clientes remotos pidiendo el mismo mes de ANCAP al mismo
tiempo con la caché vencida podrían pisarse el archivo temporal y uno de los dos recibe una
respuesta corrupta o un error de lectura a mitad de escritura. Mitigación: test de concurrencia real
(dos hilos, mismo archivo, uno simula una descarga lenta) antes de marcar esto resuelto.

## 2. Límite de pedidos (rate limiting)

Dos capas, con responsabilidades distintas:

**Capa de borde (nginx, si se despliega detrás de uno):** protege contra flood puro de HTTP
independientemente de si pega a una fuente o a la caché. Fuera del alcance de este repo —
documentado en el README de despliegue, no en código.

**Capa de aplicación (`src/mcp_uruguay/remoto.py`, este cambio):** un limitador de token bucket
por IP de cliente, en memoria de proceso (un solo proceso uvicorn, sin estado compartido entre
réplicas — si algún día se escala a más de un worker, esto tiene que pasar a Redis o similar; con
el tráfico esperado de este nicho, un proceso alcanza). Default conservador:
`MCP_URUGUAY_RATE_LIMIT_POR_MIN` (default 30 llamadas a herramienta por IP por minuto) y
`MCP_URUGUAY_RATE_LIMIT_RAFAGA` (default 5, ráfaga instantánea permitida). Al excederse, HTTP 429
con `Retry-After` en segundos — nunca bloquear la conexión indefinidamente.

Nota importante: esto protege al servidor y de rebote a las fuentes (BCU, ANCAP, OSE...) del tráfico
que un cliente mal configurado podría generar reintentando sin backoff, pero el techo real para
las fuentes más lentas (`leyes`, `compras_estado`, `proyectos_parlamento`, con TTLs de caché de 1 a
365 días) ya está puesto por esos mismos TTLs: salvo la primera vez, casi todo pedido sale de caché
y no toca la red.

**Cómo falla si esto está mal:** sin límite, un cliente MCP con un bug de reintento infinito (ya
pasó una vez, ver comentario de `IncompleteRead` en `servidor.py`) podría, en el peor caso, generar
suficiente tráfico concurrente de *cache miss* como para que varias fuentes lentas reciban pedidos
simultáneos de la misma IP. Mitigación: el límite por IP, no por herramienta — más simple y cubre el
caso real sin modelar 29 políticas distintas.

## 3. `diagnostico()` y la ruta del disco

**Qué pasa hoy:** `diagnostico()` devuelve `directorio: str(cache.directorio())`, que en una
máquina real es algo como `/home/<usuario>/.cache/mcp-uruguay` — expone el nombre de usuario del
sistema y la estructura de filesystem del servidor a cualquier llamador remoto. Los nombres de
archivo individuales (`archivo` dentro de cada `ArchivoCache`) ya son relativos
(`ruta.relative_to(d)`), así que no hace falta tocarlos.

**Decisión:** `diagnostico()` toma un parámetro `remoto: bool = False`. El valor por defecto
(`False`, stdio/local) no cambia: sigue devolviendo la ruta real, porque ahí el llamador es el mismo
usuario de la máquina y la ruta es información útil para depurar. Cuando `remoto=True`, el campo
`directorio` se reemplaza por el string `"(oculto en modo remoto: ver nota)"` y la `nota` explica por
qué. `servidor.py` sabe en qué modo está corriendo (lo decide `main()`) y pasa el flag.

**Cómo falla si esto está mal:** sin la redacción, cualquier cliente de internet puede listar el
username del servidor — bajo impacto solo porque el servidor es de solo lectura y sin otros
secretos en ese directorio, pero es higiene básica de no regalar información gratis.

## Qué queda explícitamente fuera de este plan

- **Autenticación:** el propio M8 ya concluye que "como los datos son públicos y de solo lectura,
  un despliegue HTTP sin autenticación es viable" — no se agrega una capa de auth.
- **Escalado a más de un worker/réplica:** el rate limiter en memoria de proceso no sobrevive a eso;
  si el tráfico lo exige en el futuro, ese es el momento de mover el estado a Redis, no antes.
- **TLS:** se asume un reverse proxy (nginx/Caddy) terminando TLS delante de este proceso; el
  proceso uvicorn escucha en `127.0.0.1` por defecto, nunca expuesto directo a internet.
